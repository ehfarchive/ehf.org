# EHF Static Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a faithful, responsive, frontend-only static recreation of EHF.org, including its current public navigation and genuine static editorial content while excluding all Fellow Directory functionality.

**Architecture:** Build one Astro site that renders shared layouts and repeatable page templates at build time. Capture the live source first, normalize static content into typed collections, store permitted assets locally, and add JavaScript only for visible interactions. Treat the homepage, listing pages, articles, and standard institutional pages as separate templates that share one measured design system.

**Tech Stack:** Astro, TypeScript, CSS custom properties, Astro content collections, Vitest, Playwright, axe-core, npm

---

## Scope and Decisions

### Included

- Homepage.
- Current primary navigation and footer destinations.
- Impact in Action listing, pagination, and static posts.
- Current news, events, annual-report, about, history, values, contact, media, donation, privacy, and terms content that is intentionally public.
- Desktop dropdown navigation and mobile full-screen navigation.
- Local media, fonts, icons, downloadable documents, and responsive image variants where permission allows.
- Static or externally connected newsletter and donation affordances, with the exact behavior documented before implementation.

### Excluded

- `/fellow-directory`, `/fellow-directory-advanced-search`, `/fellow-detail`, `/alumni-directory`, `/alumni-directory-advanced-search`, and directory-related iframe or data services.
- Hillary Institute pages.
- Squarespace editing, commerce, authentication, member areas, analytics, and production form backends.
- Duplicate, malformed, staging, test, and obsolete paths discovered in the Squarespace sitemap.

### Mandatory Spike Gate

The full-site plan is conditional. Before inventorying and migrating the complete site, build and evaluate exactly four representative routes:

| Route | Template being tested | Why it is in the spike |
|---|---|---|
| `/` | Bespoke landing page | Tests the hardest responsive composition, gradients, logo motion, alternating sections, and custom spacing. |
| `/read` | Collection listing | Tests repeated cards, content ordering, image crops, and the future pagination model. |
| `/read/how-chemergy-is-changing-the-game-in-waste-to-energy` | Long-form article | Tests extracted Markdown, figures, captions, links, typography, and next-article treatment. |
| `/23-annual-report` | 2022/23 annual-report and financial-statements page | Tests a fourth layout, the annual-report and financial-statement downloads, and source attribution. |

The spike includes the shared header, desktop dropdowns, mobile menu, footer, and local assets needed by these four routes. It does not include a complete sitemap crawl, bulk post migration, other institutional routes, production forms, redirects, or deployment.

After the spike verification task, write `SPIKE-RESULTS.md` and stop. The only allowed gate decisions are:

- `GO`: Astro and the proposed architecture are accepted; continue with Tasks 2–14.
- `ADJUST`: keep Astro provisionally, revise the documented architecture or workflow, and rerun affected spike checks.
- `STOP`: do not continue the Astro implementation; preserve evidence and choose a different approach.

Only the project owner can approve `GO`.

### Definition of Done

- Every approved route is generated by `npm run build`.
- All approved internal links resolve in the generated site.
- No final HTML, CSS, JavaScript, font, image, icon, or document URL depends on a Squarespace domain.
- Header, desktop dropdowns, mobile menu, pagination, lightboxes, and other captured interactions work with keyboard and pointer input.
- Playwright route, interaction, accessibility, and responsive suites pass.
- Source and implementation screenshots have no unresolved P0, P1, or P2 visual differences.
- `README.md`, the route inventory, asset manifest, and visual QA report describe the final state accurately.

- [ ] **Step 3: Implement the explicit classifier**

Create `src/utils/routes.ts` with three explicit outcomes:

```ts
export type RouteDisposition = 'include' | 'exclude' | 'review';

const excludedPrefixes = [
  '/fellow-directory',
  '/fellow-detail',
  '/alumni-directory',
  '/copy-060421-exact-match-fellow-directory'
];

const includedPrefixes = [
  '/',
  '/read',
  '/watch',
  '/news',
  '/news-blog',
  '/events',
  '/about-ehf',
  '/our-journey-and-history',
  '/our-values',
  '/annual-reports',
  '/contact-us',
  '/media-inquiries',
  '/donate',
  '/privacy-policy',
  '/terms-of-use'
];

export function classifyRoute(pathname: string): RouteDisposition {
  if (excludedPrefixes.some((prefix) => pathname === prefix || pathname.startsWith(`${prefix}/`))) {
    return 'exclude';
  }

  if (includedPrefixes.some((prefix) => pathname === prefix || prefix !== '/' && pathname.startsWith(`${prefix}/`))) {
    return 'include';
  }

  return 'review';
}
```

export function paginate<T>(items: T[], pageSize: number): T[][] {
  if (!Number.isInteger(pageSize) || pageSize < 1) {
    throw new Error('Page size must be a positive integer');
  }
  return Array.from({ length: Math.ceil(items.length / pageSize) }, (_, index) =>
    items.slice(index * pageSize, (index + 1) * pageSize)
  );
}

## Execution Strategy

### Stage 1

Keep the spike tightly integrated. One agent owns the shared Astro scaffold and shell; up to two subagents may independently capture source evidence and prepare page-specific content/assets. The integrator owns all shared CSS, final screenshots, `SPIKE-RESULTS.md`, and the gate recommendation.

Do not use broad content-migration parallelism during the spike. The objective is to test the architecture with four page types, not optimize throughput.

### Stage 2

After the project owner approves `GO`, use a maximum of three implementation subagents plus one integrator:

1. **Capture and assets:** Tasks 2–4.
2. **Shared shell and homepage:** Tasks 5–8.
3. **Content and templates:** Tasks 9–11.
4. **Integrator:** reviews every task boundary, resolves shared-file conflicts, then owns Tasks 12–14.

Tasks 2–4 must expand the spike evidence and asset inputs to the approved full route set before further visual implementation proceeds. Tasks 5–8 and Tasks 9–11 can then run in parallel with explicit ownership of shared layouts. Reuse spike code that passed the gate; do not rebuild it from scratch. Accessibility, link verification, and visual QA remain blocking integration gates.
